# Ledgerly Render deployment checklist

The backend is defined by the root-level `render.yaml` and stores production data in Supabase PostgreSQL. Render needs one secret that must never be committed: `DATABASE_URL`.

## Before deployment

- [x] Repository default branch is `main`.
- [x] Backend root directory is `backend`.
- [x] Runtime is Python `3.12.4`.
- [x] Production dependencies are pinned in `backend/requirements.txt`.
- [x] Build command installs only production dependencies.
- [x] `python -m uvicorn app.main:app` loads the canonical FastAPI entry point.
- [x] Uvicorn binds to `0.0.0.0` and Render's dynamic `$PORT`.
- [x] Proxy headers are enabled for Render's TLS-terminating proxy.
- [x] `/ready` is configured as the service health check and queries PostgreSQL.
- [x] `SECRET_KEY` is generated by Render.
- [x] `CORS_ORIGINS` is exactly `https://ledgerly-one-xi.vercel.app`.
- [x] `psycopg` is pinned for PostgreSQL connectivity.
- [x] Versioned SQL migrations run automatically during FastAPI startup.
- [x] `DATABASE_URL` is a secret input and no SQLite disk is mounted.
- [x] Deploys trigger only after GitHub checks pass.
- [x] Production rejects wildcard CORS, missing origins, and weak secrets.

## Deploy

Open the [Ledgerly Render Blueprint](https://render.com/deploy?repo=https://github.com/Saidur-droid/ledgerly), sign in if needed, and apply the Blueprint. Set `DATABASE_URL` to the Supabase **session pooler** URI and append `?sslmode=require`.

The Blueprint creates:

- `ledgerly-api`, a Starter Python web service in Singapore;
- a managed Supabase PostgreSQL connection supplied as a secret;
- a generated production signing secret;
- the exact Vercel production origin allowlist;
- health checks and CI-gated automatic deploys.

## Verify after Render reports “Live”

Replace `<backend-origin>` with the assigned `onrender.com` origin.

### Health

```bash
curl https://<backend-origin>/health
```

Expected:

```json
{"status":"ok","database":"postgresql"}
```

### Database readiness

```bash
curl https://<backend-origin>/ready
```

Expected:

```json
{"status":"ready","database":"postgresql"}
```

Render uses this endpoint for service health, so a deployment is not marked
healthy when PostgreSQL cannot execute `SELECT 1`.

### CORS

```bash
curl -i -X OPTIONS https://<backend-origin>/api/v1/auth/register \
  -H "Origin: https://ledgerly-one-xi.vercel.app" \
  -H "Access-Control-Request-Method: POST"
```

Expected response header:

```text
access-control-allow-origin: https://ledgerly-one-xi.vercel.app
```

An untrusted origin must not receive that header.

### API documentation

Open:

```text
https://<backend-origin>/docs
```

Confirm the authentication, uploads, Pulse, chat, memory, and PDF report endpoints are present.

### Complete smoke test

From the `backend` directory:

```bash
python scripts/smoke_test.py --api-url https://<backend-origin>
```

Expected final line:

```text
PASS: CSV -> persistence -> metrics -> Pulse -> dashboard -> question-aware chat -> PDF
```

## Optional Gemini activation

The initial deployment works without a Gemini key by using Ledgerly's deterministic, data-grounded explanation fallback. To enable Gemini later, add `GEMINI_API_KEY` in the Render service's Environment page and redeploy. This is not required for the backend's first successful deployment.

## Database operations

SQL migrations live in `backend/migrations`. On startup, Ledgerly applies each pending migration transactionally and records it in `ledgerly_schema_migrations`. This keeps deployments repeatable without requiring the Supabase CLI. Never commit a database password or a complete connection URI.
